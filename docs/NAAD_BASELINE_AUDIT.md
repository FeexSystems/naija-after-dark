## Startup diagnosis

The project-relative Unity log provides a more specific failure classification than the timeout alone. During AssetDatabase startup, Unity emitted repeated errors while watching `game/unity/Library/PackageCache`, including:

- `System.ComponentModel.Win32Exception (5): Access is denied.`
- `System.IO.InternalBufferOverflowException: Too many changes at once in directory ... Library/PackageCache/...`

The errors span many package-cache directories, followed by worker startup and shutdown without reaching `NAAD.Editor.Editor.ListPackages`. This indicates a local Windows file-watcher/permissions or cache-churn problem during import. It is not evidence of a package-version incompatibility or a C# compile failure. The appropriate next investigation is environment/cache access and a clean isolated Unity workspace, not a manifest or lockfile rewrite.

To test whether interrupted cache contents were the cause, the generated `game/unity/Library` directory was moved to the recoverable backup `game/unity/Library.validation-backup-20261023-134955` and Unity was launched again with the same exact-editor package-list command. The clean-cache attempt reproduced the same `Library/PackageCache` watcher errors and stalled at the initial AssetDatabase refresh. This rules out the old cache contents as the sole cause; the remaining blocker is the local Unity/file-watcher environment or the volume's access behavior.

A second retry was run after the reported Windows restriction was resolved, using the same exact editor and `NAAD.Editor.Editor.ListPackages` entry point. Unity Personal licensing and editor initialization succeeded, but the process again stopped at `Application.AssetDatabase Initial Refresh Start`; the log again contains Win32 access-denied and `InternalBufferOverflowException` watcher failures across package-cache directories. The method did not execute and no package inventory was produced. The blocker remains reproducible in this checkout and should be resolved by changing the Unity workspace/volume or endpoint-security policy before relying on local batch verification.

## Unity CLI integrity check

The Unity CLI `1.0.0-beta.13` project verifier was run read-only against `game/unity`:

```text
unity projects verify C:\\NAAD\\naija-after-dark\\game\\unity --format json --no-pager --non-interactive
```

Result before metadata repair: **failed**, with 43 errors across 10,083 scanned files. Findings included missing `.meta` files beside tracked NAAD C# assets and directories, missing metadata beside ignored generated `.gen.csproj` files, and a `MANIFEST_INVALID` category. Stable Unity-compatible `.meta` files were added for the 10 tracked NAAD C# assets and two tracked directories. A repeat verifier run reduced the result to 33 errors, all currently reported against ignored generated `.gen.csproj` files plus remaining manifest/integrity categories. Generated project files were not deleted and no production assets were rewritten.

For isolation, a disposable copy at `C:\\NAAD\\unity-cli-validation` was created without generated `.csproj` files and verified with the same Unity CLI command. Result: **passed**, zero errors and zero warnings across 10,064 files. This confirms the tracked metadata repair is clean; the repository-path verifier failure is limited to ignored generated project files and cannot be used as compile evidence until Unity Editor startup/package resolution is available.

The supported Unity CLI batch path was then exercised against that clean copy:

```text
unity run C:\\NAAD\\unity-cli-validation --timeout 120 --log-file C:\\NAAD\\unity-cli-validation-run.log --no-tail -- -nographics -executeMethod NAAD.Editor.Editor.ListPackages
```

Result: **timed out after 120 seconds** at `Application.AssetDatabase Initial Refresh Start`. No package listing or compile result was emitted. This reproduces the editor import blocker through the Unity CLI itself; extending the timeout is unlikely to provide useful evidence without fixing the underlying Windows watcher/access behavior.

The same clean-copy run was repeated with the Unity CLI `--no-accelerator` option and a 90-second bound. It also timed out before package resolution, so the configured Accelerator/cache endpoint is not the sole cause.

The serialized build scene list was reconciled with `NaadSceneNames.AllScenes` and `docs/UNITY_SCENE_REGISTRY.md`. `EditorBuildSettings.asset` now contains the six canonical enabled scenes in order: Bootstrap, Apartment, CityStreet, SuyaSpot, Nightclub, and Beach. GUIDs were copied from the corresponding scene `.meta` files.

The non-Unity asset-pipeline test phase found one mapping defect in `tools/unity-asset-pipeline/naad_addon/rules.py`: unknown venues returned the default venue's district (`ML`) instead of the documented default district (`ND`). The fallback now uses `DEFAULT_DISTRICT`; all 16 asset-pipeline unit tests pass and the Python sources compile successfully.

Filesystem ACL inspection showed full access for Authenticated Users, SYSTEM, and Administrators on the isolated `Library` and `Library/PackageCache` roots. A final isolated run with Unity's `-noUpm` flag and `NAAD.Editor.Editor.VerifyProject` also timed out at AssetDatabase startup. This indicates the issue is broader than the Accelerator or Package Manager connection and remains an editor/file-watcher startup problem.

Unity's `-disableDirectoryMonitoring` launch flag was also tested through the CLI against the clean copy. It timed out at the same startup stage, so that flag does not resolve the issue in editor `6000.7.0b4`.

An isolated copy at C:\NAAD\unity-validation was created excluding generated folders and retried with Unity 6000.7.0b4. It reproduced the same AssetDatabase refresh stall before ListPackages, so the failure is not caused solely by the repository's existing Library cache or checkout path. The isolated copy and log remain outside the repository.
